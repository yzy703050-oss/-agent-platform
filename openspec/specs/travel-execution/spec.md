# travel-execution Specification

## Purpose
让差旅 Agent 成为平台统一执行体系中的独立能力，在规划、查询、校验和保存阶段共享身份、任务与恢复管理，同时通过回执和执行围栏保护业务写入，避免恢复时重复产生变更。

## Requirements

### Requirement: 独立差旅执行
系统 SHALL 依据会话的差旅归属执行差旅 Agent，并复用现有任务、事件、页面归属及执行限制；普通聊天不自动委派差旅任务。

#### Scenario: 差旅提交
- **WHEN** 用户在就绪的差旅会话发送请求
- **THEN** 系统创建平台 Run，执行差旅规划及业务工具，不启动第二套身份或任务系统

#### Scenario: 分别可用
- **WHEN** 一个 Agent 未就绪而另一个已就绪
- **THEN** 系统分别报告可用状态，不因其中一个不可用就误判另一个

### Requirement: 有限编排与确定性业务保护
系统 MUST 对规划、查询、校验、修正及重排设置可验证的执行边界和限制；模型不能跳过业务校验或以自然语言声明代替实际提交。系统 SHALL 按已授权运行流程由Main首次规划，工具后直接交规划总结审查、修正和重排，仅真实差旅政策前置允许一次Main续规划；独立查询总结保持原范围。旧Verifier权限保留为冻结基线，不作为当前规划总结的整体修复上限。预算按原版业务批次语义累计，恢复不清零。

#### Scenario: 修正与重规划
- **WHEN** 校验发现局部问题或需要全局调整
- **THEN** 系统在允许范围内修正或重规划，达到限制则明确停止，不无限循环

#### Scenario: Verifier 权限
- **WHEN** 已有计划进入审查
- **THEN** 当前规划总结允许选择和原子修改当前授权行程，整体路线问题直接amend/route_tasks并提交受影响查询，保留硬要求与有效成果，不交回Main、不新建替代计划或读写偏好；旧Verifier仍维持基线权限

#### Scenario: 独立查询总结
- **WHEN** 用户仅查询信息且没有规划延续或已有行程待审查
- **THEN** 系统总结真实查询结果，不创建行程；真实政策观察仅按唯一例外允许Main一次续规划，已有行程及后续工具结果交规划总结

### Requirement: 业务写入幂等与回执
系统 MUST 为业务写入保存稳定逻辑操作标识、请求摘要及实际回执，恢复不重复提交已成功操作；同一操作标识不得用于不同有效参数。

#### Scenario: 提交后断点前退出
- **WHEN** 行程修订及回执已提交，执行在保存后续断点前退出
- **THEN** 后续恢复或重放从回执获取原结果，不重复新增行程修订

#### Scenario: 不同参数复用标识
- **WHEN** 同一任务中的逻辑操作标识被用于不同有效参数
- **THEN** 系统返回幂等冲突，不覆盖原操作结果

#### Scenario: 结果未知
- **WHEN** 操作可能产生了副作用但没有可靠成功或失败证据
- **THEN** 系统停止自动重放并明确结果待核实，不宣称已安全恢复或撤销

### Requirement: 差旅安全暂停与手动恢复
系统 MUST 遵循现有页面级暂停规则，只有执行停止且有效兼容断点已保存才报告 paused；重新打开不自动执行，继续前核验断点、业务回执及引用的证据。

#### Scenario: 页面切换与关闭
- **WHEN** 用户在页面内切换会话，随后关闭发起页面
- **THEN** 切换不暂停原任务，关闭被确认后请求安全暂停，不能把 SSE 断开直接等同于页面关闭

#### Scenario: 手动继续
- **WHEN** 用户重新打开并显式继续具有有效差旅断点的任务
- **THEN** 系统恢复同一 Run 的阶段状态及允许的上下文，已成功的写操作不重复执行

#### Scenario: 不兼容或保存失败
- **WHEN** 断点版本不兼容、写入失败或执行停止无法确认
- **THEN** 系统明确不可恢复，不显示虚假的可继续状态

#### Scenario: 启动兼容性检查
- **WHEN** 服务启动核验旧任务的恢复能力但用户尚未点击继续
- **THEN** 核验不调用模型、外部查询或写业务数据

### Requirement: 替代任务的信息隔离
系统 MUST 在新问题替代暂停差旅任务时使旧断点失效，并从后续自动上下文排除旧任务的消息、结果、偏好和派生摘要；保留显示历史不等于允许继续使用旧信息。

#### Scenario: 新问题替代
- **WHEN** 用户没有选择继续，而在暂停会话直接发送新问题
- **THEN** 旧任务取消并不可恢复，新任务不自动绑定旧行程或加载旧任务信息，历史仍可查看

#### Scenario: 迟到业务写入
- **WHEN** 被替代任务或旧 attempt 在新任务启动后尝试提交业务修改
- **THEN** 系统拒绝有效状态写入，不修改新任务或其行程数据

### Requirement: 批次预检与可恢复执行
系统 MUST 在产生副作用前预检完整工具批次，保留原版请求类型一致、政策前置依赖、重规划独立提交、同一行程每批一次写入和有界独立动作并发规则；合法独立动作可以同批执行，每项回执与工具调用完整配对。

#### Scenario: 整批参数无效
- **WHEN** 同批工具中任一调用的预检参数或权限不合法
- **THEN** 系统在副作用发生前拒绝该批次，并提供原因及被连带中止调用的对应结果

#### Scenario: 合法独立写入
- **WHEN** 一个批次包含不同授权行程的写入或明确偏好更新与规划，且没有真实前置依赖
- **THEN** 系统按原版规则允许该批次，不以“每轮最多一个业务修改”的额外限制拒绝；同一行程仍不得并发覆盖

#### Scenario: 批次中断恢复
- **WHEN** 批次部分动作已提交，进程在后续动作或自动查询前暂停
- **THEN** 系统依据已接受决策、逐项回执和待查作业恢复，已提交动作不重复写入，未完成动作不冒充已完成

### Requirement: 正常规划通常两次模型调用
系统 SHALL 采用用户query→Main首次规划→程序工具→规划总结Agent的正常路径。Main MUST 只承担一次首次规划；仅真实差旅政策前置结果允许再调用一次Main续规划。工具结果、参数纠错、交互恢复及整体重排 SHALL 由规划总结Agent继续处理，不因request_replan重新进入Main。常规无冲突时规划总结一次选择并总结、绑定实际回执，通常两次规划模型调用；真实重查/修复仍有界，全部实际请求按真实角色计数，包括政策、维护、压缩及协议再生成，不将两次设为总调用硬上限。

#### Scenario: 无冲突往返
- **WHEN** 可用日期、起点或授权默认已具备且候选满足要求
- **THEN** Main一次形成完整tripplan与查询地图，程序查询后直接handoff规划总结，后者一次选择并绑定总结；Main=1、规划总结=1，不重复历史读取或另加总结模型

#### Scenario: 已有记忆
- **WHEN** 正常请求已有有效注入记忆
- **THEN** Main及规划总结直接使用记忆，Main仍仅一次，不增加资料读取或偏好分析轮次

#### Scenario: 政策先于规划
- **WHEN** 明确出差或要求企业政策且缺少适用观察
- **THEN** 先发出RAG工具、观察结果后允许Main一次续规划；Main最多两次，政策提取辅助模型单列计数，不能把query_policy与依赖它的写入放同批

#### Scenario: 总结发现需重排
- **WHEN** 规划总结发现没有直达或整趟路线/日期衔接需调整
- **THEN** 它在当前这次模型调用直接提交当前行程的amend/route_tasks与查询地图，由程序执行；新结果回来再由规划总结审查选择，不先发request_replan或再次Main，不新建替代计划，不重置预算

#### Scenario: 南京中转固定返程硬一晚
- **WHEN** 上海→杭州直达无候选，用户允许经南京且去程可调、29日固定返程与杭州硬一晚
- **THEN** Main首轮后规划总结同次发现问题并改28日同日中转、杭州28至29日一晚、保留29日返程，工具后再次规划总结选择；确定性正常工具夹具下Main=1、规划总结=2、总计3

#### Scenario: 错误不触发Main第二次规划
- **WHEN** 首次Main的工具参数被拒绝、或生成追问/无效协议需要有界重新生成
- **THEN** 后续恢复以规划总结角色和其实际工具集进行；没有政策前置时Main实际生成最多一次，拒绝原文与全部真实调用保留，不能只改统计名称而继续使用Main输入

#### Scenario: 查询与保存不增加模型
- **WHEN** 已提交待查项或选择与绑定回复已保存
- **THEN** 程序直接执行查询或呈现对应回执，handoff自身不额外发模型请求，不为复述已保存结果再次调用模型

### Requirement: 无进展调用不作为正常轮次
系统 MUST 复用本轮仍有效的查询结果及已保存选择，不重复执行相同查询或以重复选择、重复读资料、重复解释作为业务进展。额外调用 SHALL 对应真实前置依赖、维护或修复原因；没有真实原因的额外轮次及无进展重复动作作为效率退化报告，保留完整轨迹，不能只以最终保存成功判为正常路径通过。评测 SHALL 报告两次路径占比及全部额外调用原因，不把两次当全场景硬门槛。

#### Scenario: 重复查询
- **WHEN** 同一查询既出现在 tripplan 自动待查项又被模型独立请求，且条件和证据有效性相同
- **THEN** 系统复用一次实际查询结果，不重复请求供应方；实际调用与去重结果均可审计

#### Scenario: 重复选择
- **WHEN** 模型重复提交与本轮已保存结果相同且无新依据的候选选择
- **THEN** 系统复用有效结果并按真实收尾条件结束，不能为重复解释继续调用模型；审计明确记为重复动作，不能用回执幂等掩盖多余模型调用

#### Scenario: 真实修复
- **WHEN** 实际候选与用户硬要求存在冲突，或查询失败、证据过期，需要真实局部修复
- **THEN** 系统保留原有有界纠错和业务校验，额外调用与具体原因对应；此样本单列异常路径，不冒充正常两次通过，也不能为了两次限制取消必要校验

### Requirement: 规划总结限定当前请求且保护硬要求
规划总结 SHALL 使用独立可信角色及运行profile。已持计划时仅能修改/选择当前允许的计划，不能新建替代计划或跨计划写入；首次Main未保存成功时只允许恢复本请求。系统 MUST 在提交前保护原有用户/context硬日期、预算、晚数及活动，路线变更只调整获准的软条件，保留有效候选，使用原有预检、事务、回执、限额和恢复机制。

#### Scenario: 不能借重排改硬条件
- **WHEN** 规划总结改固定返程、增减硬晚数、提高硬预算或删除/移动硬活动日期时段
- **THEN** 批次在副作用前拒绝，返回字段与保留要求的纠错指引，不放宽要求或回Main重置执行

#### Scenario: 计划范围及独立查询隔离
- **WHEN** 规划总结提交不在当前请求授权范围的计划ID，或独立查询Summary尝试写行程
- **THEN** 拒绝写入；只有规划总结有获准的当前计划重排能力，独立查询Summary仍只回答所问

#### Scenario: 恢复与实际调用一致
- **WHEN** 在handoff、重新生成或重排查询中断后恢复
- **THEN** 保存角色、Main已调用及政策续规划标志、输入和实际工具集；已接受决策及已完成动作重放不重新发Main、重复写入或重复查询
