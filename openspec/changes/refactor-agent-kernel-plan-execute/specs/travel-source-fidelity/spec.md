## ADDED Requirements

### Requirement: 历史基线追溯与新协议边界
系统 MUST 保留冻结 Python 基线及历史报告供追溯，但新内核运行时 SHALL 使用本次确认的角色、计划与修改协议。权限、来源、事务和回执语义需映射核验；旧软硬条件筛选已由来源优先与模型规划替代，不得通过修改历史材料掩盖差异，共享查询能力重新按当前工具契约暴露，正式计划执行不采用旧批次协议。

#### Scenario: 历史核对
- **WHEN** 审查新旧内核差异
- **THEN** 冻结材料和旧报告保持原样，新文档明确哪些流程被替换、哪些保护继续保留

#### Scenario: 新协议
- **WHEN** 新内核处理计划创建、修改或执行
- **THEN** 使用经确认的新协议，要求来源、优先次序、显式清空和修订保护均可核验，不以旧工具名称定义新业务入口

### Requirement: 新计划的完整需求与来源审查
系统 MUST 为相应决策阶段提供原请求、最新修改、当前正式计划、相关事实、政策和有效偏好；审查覆盖完整请求范围，不以首段或字段齐全替代目标满足。记忆与历史信息必须遵循来源有效性，断点兼容保护、提示词设置与分层组织、已确认记忆压缩阈值沿用既有设计；与新业务职责冲突的旧默认值或控制指令按本change适配，不通过沿用机制恢复已移除行为。

#### Scenario: 多任务覆盖
- **WHEN** 用户要求多个目的地、活动、住宿和返程
- **THEN** 计划和审查覆盖全部已提出要求，缺失内容实际修正或明确未满足

#### Scenario: 政策依赖
- **WHEN** 明确出差且政策影响规划
- **THEN** 在确定受影响的初始条件前取得政策依据，资料不足不等于无限制

#### Scenario: 历史来源
- **WHEN** 计划使用记忆或前次查询信息
- **THEN** 保存可追溯来源并检查有效性，不读入被隔离来源或将旧候选直接当作新事实

### Requirement: 计划修正的有限性与真实结果
系统 SHALL 在经确认的预算、证据刷新和无进展边界内校正计划，提供可执行的错误信息；已知能力缺口必须保留真实状态，不通过重复选择或编造事实消除未知。循环结束按travel-execution：默认最多8个“执行＋重新规划”轮次，连续2轮无实质进展结束并返回真实已有结果与未完成原因，恢复不清零。

#### Scenario: 无进展
- **WHEN** 计划与证据不变且只有重复解释或相同选择
- **THEN** 系统识别无进展并按确认的限制处理，不把它作为新增业务成果

#### Scenario: 报价缺口
- **WHEN** 酒店供应方没有报价
- **THEN** 保留价格未知和相关政策未核验状态，不用再次选择同一酒店伪装已核实

#### Scenario: 参数错误
- **WHEN** 修改或执行参数非法
- **THEN** 返回可定位字段和根因的错误，模型按当前请求及来源优先级修正，程序不伪造参数或证据使错误看似消失

### Requirement: 新决策角色的运行时职责一致
系统 SHALL 按新角色提供一致提示、适用规则和标为数据的动态上下文；初始规划、计划执行和修改提议各有明确职责，查询任务不得被提示扩展为未请求的完整行程。公共规则与参数语法有明确维护归属。

#### Scenario: 纯查询与规划分界
- **WHEN** 用户仅查询酒店
- **THEN** 两个入口的角色输入允许直接调用查询工具，不生成最小酒店计划；进入正式规划后只由计划执行器执行 Task 查询

#### Scenario: 沿用提示词设置和组织
- **WHEN** 系统装配双入口或专业规划角色的提示
- **THEN** 复用既有分层、统一组装/替换及兼容指纹机制，按实际角色和工具调整变化内容；动态上下文仍作为数据，不因切换或重试丢失或重复规则

#### Scenario: 修改阶段
- **WHEN** 已有计划需要修正
- **THEN** 决策输入要求基于当前版本提出增量修改，不同时要求重建替代计划

#### Scenario: 参数说明
- **WHEN** 模型生成计划或 Patch
- **THEN** 接收对应有效 Schema 和字段规则，不混入已移除工具的参数指令

### Requirement: 新角色重试与恢复的可核验性
系统 MUST 在首次调用、重试和恢复时保持实际角色、有效提示、可执行能力和审计一致；提示、契约及组装版本参与兼容指纹，不兼容断点不得虚报可恢复。

#### Scenario: 协议修正
- **WHEN** 模型输出需要按经确认的规则修正
- **THEN** 使用当前阶段的有效职责和协议，不因重试回到旧 Main/总结控制流程或扩大权限

#### Scenario: 停止与兼容性
- **WHEN** 执行已停止或旧断点与新内核不兼容
- **THEN** 不重新开放执行权限，不伪称无缝兼容，历史仍可读取

## REMOVED Requirements

### Requirement: 原版提示与工具契约保真
**Reason**: 用户明确新逻辑不受旧 Agent 流程约束，旧工具名称和旧角色路径不能继续作为新内核的冻结接口。
**Migration**: 由“历史基线追溯与新协议边界”替代；保留冻结历史材料、来源和业务保护，新运行协议独立确认与版本化。

### Requirement: 完整需求驱动的审查与校正
**Reason**: 旧条款包含默认往返及旧记忆维护流程，需要从新请求范围与来源规则重新表达。
**Migration**: 由“新计划的完整需求与来源审查”替代；保留完整需求、政策前置和有效来源保护，缺参和维护策略在开工前协调。

### Requirement: 有限校正与真实收尾
**Reason**: 旧条款绑定 Python 原版阈值、能力分类和 Main/总结恢复规则，不能直接作为新循环协议。
**Migration**: 由“计划修正的有限性与真实结果”替代；继续保护真实错误反馈、未知价格与无进展行为，具体结束标准须确认。

### Requirement: 差旅运行时提示职责一致
**Reason**: 旧场景绑定 Main/规划总结和固定默认值；纯查询不建计划的行为保留，角色和规划职责按最新边界表达。
**Migration**: 由“新决策角色的运行时职责一致”替代；保留职责一致、规则唯一归属和有效 Schema，改为双入口共享查询、正式规划及 Patch。

### Requirement: 差旅提示在重试与恢复中可核验
**Reason**: 旧场景要求无效 Main 输出交给规划总结，且固定旧正常调用顺序，新角色无法沿用这些阶段断言。
**Migration**: 由“新角色重试与恢复的可核验性”替代；保留审计、指纹和不兼容拒绝恢复，不宣称旧断点可直接执行新内核。
