## ADDED Requirements

### Requirement: 面向请求范围的结构化计划
系统 SHALL 支持多段出行、住宿和活动规划，也支持用户明确要求保存的单项正式安排；纯信息查询不建立计划；要求必须保留来源，按政策高于用户、用户高于记忆供模型规划和排序，不再分软硬条件筛选候选。推断或建议不得冒充用户已确认要求或供应方事实。缺少信息时由模型结合上下文判断是否可以继续，不以旧内核的固定起点、往返或时长默认自动扩展查询范围；查询必需参数尚未就绪时不发起对应查询，但可以保存当前已知的最小计划。

#### Scenario: 多段与返程
- **WHEN** 用户提出包含多个目的地和返程的需求
- **THEN** 系统保存可识别的交通、住宿及活动关联，检查相关日期与衔接

#### Scenario: 仅单项正式安排
- **WHEN** 用户明确要求建立或保存住宿安排
- **THEN** 系统保存覆盖该请求的住宿任务计划，不因使用统一计划而扩展为完整往返行程

#### Scenario: 已知要求和建议
- **WHEN** 计划包含模型建议或来自记忆的偏好
- **THEN** 系统保留实际来源及排序依据，不将其伪装为用户本轮明确确认

#### Scenario: 查询参数尚未就绪
- **WHEN** 模型结合允许使用的上下文仍未确定查询所需参数
- **THEN** 系统保存已知计划内容及未解决信息，暂不执行相应查询，不编造参数使调用看似可执行

#### Scenario: 政策检索失败
- **WHEN** 出差规划的政策检索失败或没有取得适用依据
- **THEN** 系统保留政策未核验及原因，不阻止最小计划保存；模型决定如何继续，答复不伪称已经满足政策

### Requirement: 计划变更的约束校验与依赖失效
系统 MUST 在接受计划创建或修改时校验数据表示、结构、引用和执行参数合法性，后续修改基于当前计划版本和稳定任务身份提交。模型负责日期衔接、预算和其他业务要求的规划取舍，不由程序按软硬条件筛选。被修改 Task 的查询 Item 重新查询，未改变 Task 的有效结果保留；金额、时间、车种和席别等使用规范表示。

#### Scenario: 局部修改
- **WHEN** 用户仅修改活动 Task，其他交通住宿 Task 定义未变
- **THEN** 系统保存修改并保留其他 Task 的有效结果；被修改 Task 的查询遵循重新查询规则

#### Scenario: 条件影响候选
- **WHEN** 用户改变查询日期使原选择不再适用
- **THEN** 系统取消原选择的当前有效性，安排必要查询或选择，不将旧候选继续当作有效事实

#### Scenario: 候选与要求不一致
- **WHEN** 候选没有完全符合预算、时间或其他要求
- **THEN** 系统将真实差异和未知项交给模型按来源优先级评估，不以旧软硬条件筛掉候选，也不把不满足伪装成已满足

#### Scenario: 表示规范化
- **WHEN** 等价车种、金额或时间以不同文本形式输入
- **THEN** 系统按规范值比较，不因表达差异误判，也不将未知金额变为零

#### Scenario: 活动精度
- **WHEN** 用户只给出上午等粗时段
- **THEN** 系统保留精度与来源，不补造用户未明确的精确时刻

## REMOVED Requirements

### Requirement: 结构化规划与必要追问
**Reason**: 旧条款将完整往返、固定默认起点和不追问流程绑定为所有请求的行为，与按请求范围规划、纯查询免计划的新内核方向不一致。
**Migration**: 由“面向请求范围的结构化计划”替代；采用模型结合上下文判断、参数未就绪不执行查询和规划缺参时可保存已知计划的规则，不继承旧固定默认值。多段关系、来源和建议边界继续保留。

### Requirement: 约束校验与增量修改
**Reason**: 旧条款混合了保真迁移工具语义和业务保护，需要明确新的版本化 Patch 与领域任务边界。
**Migration**: 由“计划变更的约束校验与依赖失效”及 tripplan-lifecycle 替代，采用新的来源优先与模型排序规则，保留表示规范化、Task 版本、实际结果和活动精度边界。
