## Purpose

为用户保留通用与专门差旅助手两个入口，在直接信息查询和专业行程规划之间划分职责，并将专业结果带回当前对话。规定会话信息使用及最终表达的事实边界，支持后续增加其他专业能力而无需改变用户使用入口。

## ADDED Requirements

### Requirement: 独立MCP子Agent接入
系统 SHALL 将Travel作为独立服务进程，通过受控MCP能力适配供两个入口使用，并隔离平台编排与专业执行。平台 SHALL 通过事务Outbox及MQ将子Agent调用分发给平台Dispatch Worker，再由其经MCP提交专业任务；独立服务持久受理、后台执行并提供状态/真实结果查询，不要求直接消费平台MQ，不创建第二个用户Run。双方 MUST 各管本服务状态/执行权，不跨服务直接写业务表，不因工具发现自动开放未授权能力。

#### Scenario: 独立Travel规划
- **WHEN** 当前入口发起已注册的Travel规划委派
- **THEN** 平台在本地事务保存可靠父现场、委派及Outbox后，通过MQ交给Dispatch Worker经MCP提交，Travel持久保存任务后返回受理凭据并独立执行，平台收集真实结果后恢复原调用，不再向Travel重复发送直接执行消息

#### Scenario: 受理响应丢失
- **WHEN** Travel已受理任务但平台未收到或未保存提交响应
- **THEN** 平台使用原稳定调用身份重试提交或查询，Travel对同身份同参数返回原任务，对同身份不同参数明确拒绝，不重复创建规划任务

#### Scenario: 后续专业能力接入
- **WHEN** 后续需要通过MCP接入新的外部专业Agent
- **THEN** 系统通过能力/契约和执行适配扩展，不要求复制用户会话生命周期；服务须明确授权、幂等、任务期限和结果恢复语义后才可启用

#### Scenario: 普通MCP查询工具
- **WHEN** Travel或入口调用已确认的RAG检索工具
- **THEN** 系统继续采用同步工具调用，不因Travel拆为独立子Agent而新增RAG执行任务、异步交接或任务Topic

#### Scenario: 专业任务最终明确失败
- **WHEN** 已可靠受理的专业Task明确进入failed终态，且父依赖仍有效、Run期限和授权允许恢复
- **THEN** 平台可靠收集真实失败及可用部分结果，按原调用交回父Agent处理，不自动换key或新建专业Task重做；同key重提返回原失败任务，不将其重置为queued

#### Scenario: 失败结果到达时父Run已终态
- **WHEN** 专业失败或部分结果到达时父Run已终态、全局期限已到或依赖已失效
- **THEN** 平台不恢复父执行、不自动新建专业任务，仅按授权与保留规则留存必要审计

### Requirement: 子Agent提交的持久延迟重试
系统 SHALL 使用PG not_before及Outbox轮询安排仍可重试的子Agent提交操作，资格、累计次数、稳定身份、下一次时间及唯一Outbox在平台本地事务一致保存，到期且状态/授权/期限/调度代次有效时再发送Kafka。首版不以Redis ZSET或Kafka retry Topic替代该持久调度。API工具的短退避 SHALL 使用所属执行者的可取消本地timer，不经MQ，持久调用账继续保护次数、结果与预算。

#### Scenario: 延迟提交遇到调度进程重启
- **WHEN** 平台已保存未来not_before及Outbox，调度进程在到期前退出
- **THEN** 其他有效Publisher可在该绝对时刻到期后按租约认领发送，不提前执行、不因重启重置次数或业务身份；已失效的操作不得被到期扫描复活

#### Scenario: 工具本地短退避
- **WHEN** 正在running的任务对可重试API工具执行短退避，且当前执行权及期限仍有效
- **THEN** 该执行者以可取消timer等待，继续占自身槽并独立续租，不为该工具重试额外投递Kafka或登记Redis闹钟，恢复不得清零已持久记录的实际尝试

### Requirement: 双入口共享查询与按需规划
系统 SHALL 保留通用 Agent 与专门差旅助手两个入口。两个入口均可使用已注册的查询工具直接查询交通、酒店、天气、网页和知识库，纯查询不要求建立 TripPlan 或计划 TravelThread。通用入口识别到新建行程、修改正式行程或保存计划选择的需求时 SHALL 调用差旅规划能力；差旅助手入口直接使用同一专业规划子流程，无须先调用通用 Agent。两个入口复用平台身份、权限、预算和记忆规则，不创建重复用户 Run。

#### Scenario: 通用入口酒店查询
- **WHEN** 用户在通用入口仅查询指定日期的酒店
- **THEN** 当前入口 Agent 直接调用共享查询工具并返回真实结果，不创建 TripPlan、计划工作线程或差旅规划委派

#### Scenario: 差旅入口酒店查询
- **WHEN** 用户在差旅助手入口仅查询酒店或天气
- **THEN** 差旅入口 Agent 直接调用同一查询能力，不因入口类型而强制规划

#### Scenario: 通用入口请求规划
- **WHEN** 用户要求安排旅程或修改已有正式行程
- **THEN** 当前入口 Agent 委派差旅规划能力，专业结果回到当前通用会话表达

#### Scenario: 差旅入口请求规划
- **WHEN** 用户从差旅助手入口要求安排旅程
- **THEN** 差旅入口 Agent 在当前 Run 内进入同一规划子流程，不先通过 General，不创建第二个用户 Run

#### Scenario: 多工具信息查询
- **WHEN** 用户同时查询车次和天气，但没有要求形成或修改正式行程
- **THEN** 当前入口可直接调用多个查询工具，不以工具数量作为强制委派依据

#### Scenario: 普通聊天
- **WHEN** 用户提出不需要专业规划的普通问题
- **THEN** 当前入口可直接回答，不因注册了规划能力而强制调用它

### Requirement: 正式计划的只读与修改边界
系统 SHALL 允许两个入口通过受控只读能力定位和查看当前授权范围内的正式计划。创建计划、提交 Patch、保存候选选择和刷新计划任务 MUST 进入专业规划提交边界；直接查询的结果不自动变成计划选择。入口类型不自动授权跨会话读取。

#### Scenario: 查看已有住宿
- **WHEN** 用户只问已有行程当前选择了哪家酒店
- **THEN** 当前入口读取正式版本和引用证据回答，不必启动重规划，也不修改计划

#### Scenario: 修改已有住宿
- **WHEN** 用户要求更换正式行程中的酒店或调整住宿预算
- **THEN** 系统进入对应计划工作线程处理修改，校验归属和版本，不通过查询工具直接改写计划

### Requirement: 全新数据库部署与新请求切换
系统 SHALL 由两个入口按新能力边界处理新请求，并从全新数据库结构开始部署。按用户于2026-11-07确认，旧数据库中的账号、会话、消息、计划、证据、记忆和断点均不要求保留、导入或兼容读取。旧执行者 MUST 在启用新链路前停止，旧断点不得作为新任务恢复；新运行产生的数据继续遵循本change的归属、审计、来源及恢复要求。

#### Scenario: 空库启动并提交新请求
- **WHEN** 系统按新架构部署并接收用户请求
- **THEN** 系统建立新账号和会话数据，使用新流程，不依赖旧表、历史数据或旧身份映射

#### Scenario: 旧执行状态不导入
- **WHEN** 旧数据库中存在暂停、运行中任务或断点
- **THEN** 新系统不将它们导入为可执行任务，不恢复旧断点，不要求为旧任务实现兼容收尾

### Requirement: 会话信息与业务状态延续
系统 SHALL 由当前入口 Agent 承接专业委派和明确记忆工具操作；周期记忆检查由 Maintenance 承担，检查间隔、必要性判断和后台处理遵循本 change 的 travel-memory delta。

#### Scenario: 自动记忆检查
- **WHEN** 达到每 10 轮新增有效对话的记忆检查条件
- **THEN** Maintenance 做程序检查并协调模型必要性判断，有必要才后台归纳，不阻塞当前入口答复

### Requirement: 差旅子线程上下文延续
系统 SHALL 在首次创建 TravelThread 时，从当前入口 Agent 的有效上下文中选取完成委派所需的信息，形成有来源依据的委派快照；后续继续该 TravelThread 时，读取其已有有效历史，并传入当前用户的新要求及本次调用所需的最新主 Thread 信息。该输入方式替代每次传递父级完整会话历史。系统 MUST 在处理已有计划修改时读取正式计划和有效证据，任何线程历史或快照均不得绕过既有来源隔离或替代业务状态读取。

首次委派的必要历史 SHALL 由当前入口 Agent 总结提供。后续输入 SHALL 使用原子线程记忆，加上主 Thread 自上次委派后新增相关信息的总结及当前新要求；上次差旅执行结果与重规划理由在子线程记忆中延续。新计划使用新的子线程与初始记忆，不自动复制旧计划内部执行状态。

#### Scenario: 首次创建子 Thread
- **WHEN** 当前入口 Agent 首次将一项差旅任务委派给新的 TravelThread
- **THEN** 系统提供本次委派目标及所需的有效上下文快照，保留相关用户要求和来源，不因省略无关聊天而遗漏必要条件

#### Scenario: 后续继续子 Thread
- **WHEN** 已明确继续原 TravelThread，且用户提出新的相关要求
- **THEN** 系统加载原线程的有效历史，并提供本次新要求及相关主线程更新，不仅依赖首次快照或重新复制父级全部历史

### Requirement: 计划与差旅子线程对应
系统 SHALL 为每份 TripPlan 维护对应的独立 TravelThread。新计划创建新的逻辑子 Agent 上下文，已有计划的后续修改复用原线程；同一线程可由后续 Run 继续使用，但不能混用其他计划的内部历史。首次委派可以先建立线程，再在正式创建计划后建立对应关系。

#### Scenario: 同一主线程中的新计划
- **WHEN** 用户在已有计划之外发起明确的新 TripPlan
- **THEN** 系统创建新的 TravelThread，不将原计划的内部历史直接作为新计划的子线程历史

#### Scenario: 直接查询后提出规划目标
- **WHEN** 用户先直接查询酒店，随后要求形成行程
- **THEN** 系统新建 TripPlan 与计划 TravelThread，以必要上下文和可校验的证据引用开始规划；先前纯查询没有需要继续的最小计划

#### Scenario: 原计划修改或恢复
- **WHEN** 用户明确修改已有 TripPlan，或恢复该计划尚未完成的原调用
- **THEN** 系统继续对应 TravelThread，不因 Run 改变、计划升版或调用恢复而重新创建子线程

### Requirement: 已有计划修改时加载正式状态
系统 SHALL 在已明确目标计划后加载其当前正式版本和有效证据，保持上下文与业务事实的职责分离。

#### Scenario: 已完成计划的后续修改
- **WHEN** 用户在后续消息要求调整之前计划的酒店，且目标计划已明确
- **THEN** 差旅能力使用该计划当前版本及有效结果处理修改，不仅从旧自然语言回答猜测计划内容

#### Scenario: 不可用的内部记录
- **WHEN** 上次候选细节没有进入当前入口 Agent 的消息历史
- **THEN** 系统从业务存储取得允许使用的证据，不将委派快照或 TravelThread 历史当作候选事实已经恢复的证明

#### Scenario: 来源后来失效
- **WHEN** 委派快照或子线程历史依赖的来源被排除或清除
- **THEN** 系统按现有来源有效性规则排除受影响信息，不能通过复制到 TravelThread 绕过隔离

### Requirement: 当前入口 Agent 按需定位计划
系统 SHALL 默认向当前入口 Agent 提供当前主 Thread 下与本次请求相关的计划目录及必要摘要，支持按城市、日期、标题等检索，而非无界注入全部完整 TripPlan。目录 SHALL 包含稳定计划及子线程引用、可识别的请求范围、当前修订、生命周期、真实进度摘要和更新时间；摘要不得把未知信息或未完成事项表述为已完成。

#### Scenario: 多份历史计划
- **WHEN** 当前主 Thread 下已有多份计划，用户明确指向其中一份
- **THEN** 系统提供用于定位的相关目录与该计划必要摘要，不要求当前入口 Agent 读取所有计划的完整内部内容

#### Scenario: 计划指代不唯一
- **WHEN** 用户的城市、日期或自然语言指代同时匹配多份计划，且目标仍不明确
- **THEN** 当前入口 Agent 结合有效会话上下文、用户要求和相关计划目录/摘要，自主判断合理的目标或新建计划，不因关联不明确固定追问用户；程序继续校验目标归属、计划与线程对应关系及版本

### Requirement: 模型判断新建或继续
系统 SHALL 由当前入口 Agent 结合当前用户要求、有效上下文和相关计划信息，判断新建 TripPlan/TravelThread 或继续已有计划及其线程。关联不明确本身 MUST NOT 成为强制追问或固定阻塞条件；模型的语义判断不得替代程序对实际对象存在性、访问权限、计划线程对应关系和计划版本的校验。

#### Scenario: 未明确声明新建或修改
- **WHEN** 用户提出新的差旅要求但没有明确说明与已有计划的关系
- **THEN** 当前入口 Agent 自主判断合理关联并选择新建或继续，系统不固定要求用户先指定计划或确认关联

#### Scenario: 目标引用不合法
- **WHEN** 模型选择的计划或线程不存在、不属于当前允许访问范围或对应关系不一致
- **THEN** 程序拒绝该不合法目标并返回可纠正错误，不因模型认为关联合理而放行

#### Scenario: 按需表达专业结果
- **WHEN** 用户需要查看候选、具体安排或未解决事项
- **THEN** 差旅能力提供本次所需的真实结果和来源限制，当前入口 Agent 不必读取完整内部执行历史；继续处理时仍读取并校验当前正式计划版本

### Requirement: 专业结果统一表达
系统 SHALL 允许当前入口 Agent 在收到专业结果后重新组织表达，同时保留已知事实、来源、部分结果状态及未解决事项。

#### Scenario: 酒店价格未知
- **WHEN** 差旅返回酒店地点但没有可核实价格
- **THEN** 当前入口 Agent 的最终回答继续说明价格未知，不宣称已经满足硬预算或可预订

### Requirement: 会话短期记忆与压缩
系统 SHALL 按原项目策略，以旧轮次摘要和摘要尚未覆盖的完整有效消息组装当前入口 Agent 的会话输入，保留本轮用户请求原文。默认上下文预算为 20,000 token，达到 80% 时检查压缩；预算计入系统前缀、消息和工具定义。系统 MUST 仅压缩已完成且工具配对完整的旧轮次，不压缩当前 Run；原始记录继续持久化，摘要覆盖范围不得与原文重复输入。

#### Scenario: 未触发压缩
- **WHEN** 当前有效输入未达到压缩阈值且没有已有摘要
- **THEN** 当前入口 Agent 接收允许使用的原始会话消息和本轮请求，不预先将本轮请求改写为摘要

#### Scenario: Run 内触发压缩
- **WHEN** 当前 Run 的后续模型调用使输入达到压缩阈值
- **THEN** 系统可压缩已完成旧轮次，保留当前 Run 的原始消息和工具配对；单次准备最多逐步合并三个完整旧轮次

#### Scenario: 摘要失败或预算仍不足
- **WHEN** 摘要生成失败、为空、未满足提交阈值或发生状态版本冲突
- **THEN** 系统不提交部分摘要及覆盖位置，冲突时重新读取正式状态；最终输入仍超过总预算时明确停止，不删除当前 Run 的内容以继续调用

#### Scenario: 清除上下文
- **WHEN** 用户清除当前会话上下文
- **THEN** 系统清除旧摘要并推进有效读取边界，不通过摘要重新引入已清除内容；清除上下文不等于删除原始审计记录
