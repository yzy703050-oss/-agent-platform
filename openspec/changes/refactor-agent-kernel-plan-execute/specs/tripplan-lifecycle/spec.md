## Purpose

以可追溯的 TripPlan 统一承接完整出行规划和范围有限的正式安排，使用正式版本与实际证据驱动执行。区分模型修改提案、已提交计划和查询事实；Task 保存查询定义，Item 表示查询动作，要求按来源优先级供模型规划和排序。

## ADDED Requirements

### Requirement: 多城市行程关联
系统 SHALL 在同一计划中保留有序城市停留和交通衔接，将查询、住宿及活动关联到对应行程对象；同一城市多次到访必须能区分，计划日期不得冒充已经核实的实际交通时刻。

#### Scenario: 多城旅行
- **WHEN** 用户要求北京出发、先上海再杭州并返回北京
- **THEN** 系统在同一计划中表示各次停留和交通关系，将上海、杭州住宿关联到各自停留，并依据实际查询结果核验衔接

#### Scenario: 相同城市再次出现
- **WHEN** 同一城市在计划中出现多次
- **THEN** 系统通过稳定行程对象标识区分，不能仅以城市名定位住宿或交通修改

### Requirement: 按请求范围建立统一计划
系统 SHALL 为行程规划、正式安排保存及其修改建立覆盖请求范围的 TripPlan；纯信息查询不创建计划。完整指覆盖规划请求范围，不得扩展用户未要求的往返、住宿或活动。用户明确要求只形成住宿安排时，计划可以只包含住宿 Task；出差规划所需的政策检索作为形成初始计划的前置依据。

#### Scenario: 纯酒店查询
- **WHEN** 用户仅要求查询指定城市酒店
- **THEN** 当前入口直接查询，不建立 TripPlan

#### Scenario: 仅保存住宿安排
- **WHEN** 用户明确要求建立或保存住宿安排
- **THEN** 系统通过专业规划流程创建仅包含所需住宿 Task 的计划，不虚构交通任务

#### Scenario: 只返回候选
- **WHEN** 用户要求先查看酒店候选而没有要求确定选择
- **THEN** 系统可以查询并返回候选，不把自动选中酒店作为完成本次请求的必要条件

### Requirement: 完整创建与增量修改
系统 SHALL 在首次创建计划时提交完整内容；后续同一计划的调整必须基于当前版本提交可校验的增量修改，保留稳定任务身份和未受影响内容。模型提案只有在校验和业务提交成功后才成为正式版本。

#### Scenario: 日期修改
- **WHEN** 用户修改已有酒店任务的入住和退房日期
- **THEN** 系统更新原计划版本，使受影响的酒店结果和选择失效，保留无关且仍有效的内容

#### Scenario: 旧版本冲突
- **WHEN** 修改提案引用的预期版本不再是当前版本
- **THEN** 系统拒绝直接覆盖当前计划，不产生部分修订或成功回执

### Requirement: 要求来源与模型排序依据
系统 MUST 在计划版本中保存要求的内容、作用范围和来源引用。模型 SHALL 按政策高于用户、用户高于记忆的来源优先级规划、排序和选择；兼容要求可以共同采用。系统 SHALL 不再使用 hard/soft 分类对候选做业务资格筛选，整体计划的合理性和取舍由模型负责；程序仍校验结构、执行参数合法性、权限、引用、版本和实际执行结果，不得编造已满足要求的事实。

#### Scenario: 记忆与本轮要求不同
- **WHEN** 常用出发地来自长期记忆，但本轮用户明确指定另一个出发地
- **THEN** 当前计划采用本轮要求并保留来源，不因此自动修改长期记忆

#### Scenario: 来源冲突
- **WHEN** 当前适用政策、用户要求和记忆存在相互冲突的内容
- **THEN** 模型依照政策高于用户、用户高于记忆处理，保留来源及取舍依据，程序不再以旧软硬标签执行筛选

### Requirement: Task 定义与 Item 查询动作
系统 SHALL 在 Task 中保存查询所需的详细业务信息，Item 仅声明查询动作及查询领域，不独立复制一套详细查询参数。Executor MUST 从正式 Task 及相关正式上下文解析实际执行输入；候选选择由模型提出并通过业务提交保存，不作为 select 类型的 Item。

#### Scenario: 查询输入展开
- **WHEN** 正式计划包含酒店查询 Item
- **THEN** Executor 从所属 Task 解析城市、住宿日期、人数、要求和排序信息，再交给对应查询能力

### Requirement: 查询标记与 Task 版本
系统 SHALL 根据 Task 定义版本和执行记录维护 Item 的 needs_query 状态。Task 的计划定义改变后，该 Task 下的查询 Item MUST 重新安排查询；其他未改变 Task 不因整份计划升版而重查。查询状态和结果写入不构成 Task 定义变化，模型可以请求主动重查，但不能仅修改标记就把未执行动作认作完成。

#### Scenario: Task 定义变化
- **WHEN** 已查询 Task 的计划定义发生修改
- **THEN** 该 Task 的 Item 重新成为需要查询状态，之前结果不冒充新版本已查询结果

#### Scenario: 查询成功后记录结果
- **WHEN** 查询完成并保存对应执行记录与证据
- **THEN** 程序更新查询状态，不因此修改 Task 定义并反复触发查询

### Requirement: 执行依据与事实分离
系统 SHALL 仅根据校验并接受的计划执行动作，记录实际执行输入和结果；正式计划的任务执行不得绕过已提交 Task；两个入口的独立查询不属于计划任务执行，不得以生成的价格、库存或候选标识代替证据。

#### Scenario: 未接受的草稿
- **WHEN** 模型输出包含不合法日期或未经提交的计划
- **THEN** 执行器不据此调用供应方或报告计划保存成功

#### Scenario: 未知价格
- **WHEN** 查询结果没有酒店房价
- **THEN** 系统保持价格未知，不将其当作零或已满足预算

### Requirement: 版本化结果复用
系统 MUST 依据所属 Task 定义版本、证据时效及执行授权判断结果是否可用，不因计划整体升版而无差别重查，也不将迟到旧结果直接绑定为当前有效选择。Task 定义变化后的查询安排遵循本规格的 Task 版本规则。

#### Scenario: 其他 Task 修改
- **WHEN** 用户修改一个活动 Task，而交通和酒店 Task 的定义未变
- **THEN** 系统保留仍有效的交通和酒店结果，不安排这些未改变 Task 的查询

#### Scenario: 结果在修改后返回
- **WHEN** 旧查询返回时所属 Task 定义版本已经改变
- **THEN** 系统不把旧结果标记为当前动作的有效完成，可按允许规则保留历史证据

### Requirement: 可追溯修订与原子提交
系统 SHALL 为每次接受的修改保存完整版本快照、修改依据和实际回执；修改版本指针、执行项安排与回执必须作为一致的业务提交处理。

#### Scenario: 提交中断
- **WHEN** 保存新计划或登记相关执行项时事务失败
- **THEN** 不留下只更新版本指针或只报告成功的部分状态

#### Scenario: 重放已提交修改
- **WHEN** 同一修改因恢复而重新处理
- **THEN** 系统返回原回执，不重复增加修订或安排相同执行代次
