## MODIFIED Requirements

### Requirement: 执行互斥与终态
系统 MUST 防止同一会话的任务同时执行，终态不可被迟到的结果覆盖；完成消息与成功状态必须共同持久化，存储失败不得向客户端报告完成。一个用户问题对应一个外层 Run，内部专业委派、检索和恢复不创建第二个用户 Run；新的问题不得作为补充消息注入活动 Run。

#### Scenario: 同会话并发
- **WHEN** 会话已有未结束的问答，包括其内部等待或故障恢复阶段，又收到不同的新请求
- **THEN** 系统返回 run_conflict，不启动第二个执行器，不将请求追加到旧 Run，也不自动取消旧 Run

#### Scenario: 完成与结束竞争
- **WHEN** 正常完成与系统超时或失败收尾竞争
- **THEN** 仅接受符合当前状态和执行版本的一次迁移，迟到结果不改变已提交终态

## ADDED Requirements

### Requirement: 共享额度和累计调用预算
系统 MUST 在实际模型或供应方尝试前可靠登记或预占累计预算，并对结果幂等结算；故障恢复不得重置预算或将未知消耗无依据退款。共享额度故障时不得退回每Worker各自满额，Redis切换或通知遗漏不能成为重复获得正式执行权的依据。

#### Scenario: 发起后未结算
- **WHEN** 调用已经登记预占，Worker在发送或接收结果期间崩溃
- **THEN** 恢复保留该次尝试和未知消耗，优先查询已保存结果，再在剩余预算内决定必要重算

#### Scenario: Redis切换丢失许可
- **WHEN** 新Redis主节点未保留部分旧许可，或Redis暂时不可用
- **THEN** 系统保守限制新调用，以持久调用记录保护硬额度；已有结果仍可可靠保存和交接，不允许各实例自行放满额度

### Requirement: 网络重试责任唯一
系统 SHALL 按失败类别执行有界重试，默认同一逻辑可重试操作最多重试三次、总尝试最多四次，并持久保留尝试次数。模型SDK、HTTP、任务恢复、MQ重投和MCP提交/查询必须分清职责，不叠乘同一调用的尝试。参数/授权错误、空结果和能力缺失不得无限重试；部分流式输出不得透明拼接另一调用。重投/恢复不重置专业任务或内部工具预算；发送重投、状态查询和CAS冲突重读不等于新业务尝试。

#### Scenario: 多层重投
- **WHEN** 供应方暂时故障且同一MCP委派被重复提交或恢复扫描重复发现
- **THEN** 同逻辑调用的物理尝试受统一次数、期限和预算约束，重复提交不额外启动专业任务或一套网络重试

#### Scenario: 流式半响应
- **WHEN** 模型已产生对外可见增量后连接失败
- **THEN** 保存已有草稿及真实失败原因，不将另一调用输出直接续接为原回答的完整成功结果

#### Scenario: 三次重试上限
- **WHEN** 同一逻辑调用第一次执行及后续三次重试均失败，或下一次尝试已无法落在剩余期限内
- **THEN** 系统明确结束该调用，不因MQ重投、巡检或换Worker重新获得四次尝试，不延长全局deadline

### Requirement: 全局期限与多阶段有效性校验
系统 MUST 从Run接纳起固定全局deadline，默认总期限为300秒，包含排队、父Job等待、退避及结果表达；子任务和单次尝试期限不得超过祖先允许窗口。发布/认领、MCP提交与受理、实际新调用/正式提交、结果汇聚和父恢复均须核对当前终态、授权、deadline及调度/执行代次；不能依靠Kafka日志保留或一次前置检查代替。Run全局到期后终结，不因巡检重试复活；全局未到期的局部尝试失败仅在次数/预算允许时恢复。

#### Scenario: 默认期限贯穿内部等待
- **WHEN** 使用默认配置接纳一轮Run，父Job随后异步等待子Agent并释放槽位
- **THEN** 系统保持接纳时确定的300秒总期限，恢复、续租及重试不从当前时间重新计算完整期限，超时后按终态规则收尾

#### Scenario: 队列中过期命令
- **WHEN** MQ中的旧命令被取出时父Run已终态、deadline已到或调度资格已失效
- **THEN** 消费者核对持久状态后幂等跳过，不调用子Agent，消息本身的保留不能续命

#### Scenario: 前置校验后失效
- **WHEN** 命令接纳后至子任务执行或结果回填前发生期限、授权或代次变化
- **THEN** 系统在后续有效推进和本地提交时再次校验，迟到结果仅留必要审计，不改变父终态

#### Scenario: 全局超时巡检
- **WHEN** 巡检发现Run全局deadline已到并与正常完成竞争
- **THEN** 状态条件与version/事务保护只允许一次合法终态提交，不能超时后重新排入重试

### Requirement: 逐轮问答与简化交互
系统 SHALL 按用户提问、执行并回答组织交互，不提供向活动 Run 追加要求、用户暂停、手动继续或用户主动取消整轮问答的按钮、接口或模型控制工具。系统 MUST 保留内部异步等待、工具调用与真实返回配对、执行权限和预算保护；内部挂起或进程恢复不得被解释为用户暂停。后续问题仍可按原授权和有效上下文处理既有计划，不因简化交互丢弃持续 Thread。

#### Scenario: 原请求执行中
- **WHEN** 原Agent、专业子Job或同步检索工具正在处理本轮问题
- **THEN** 系统不运行补充输入注入、父子输入归属分派或独立取消识别流程，按原请求及预算执行并返回真实结果

#### Scenario: 修改计划中的安排
- **WHEN** 用户在新一轮问题中要求取消某项行程安排或修改既有计划
- **THEN** 模型按业务意图进入相应规划修改边界，不把该业务要求当作取消整轮 Run

### Requirement: 运行限制与系统收尾
系统 MUST 为执行设置总时限、模型迭代上限、工具时限和有界重试，区分成功、超时、失败及不可恢复中断。达到限制时由程序可靠收尾并停止新的有效推进，不等待用户取消，也不允许模型重置限制；终态后原断点不得恢复执行，迟到结果不得改变终态或冒充本次正常完成。

#### Scenario: 执行达到限制
- **WHEN** 模型或工具执行达到配置上限，或整轮超过截止时间
- **THEN** 系统保存真实结果和明确结束原因，不无限调用模型或工具，不把系统超时或失败记录成用户取消

#### Scenario: 到期后的结果
- **WHEN** Run 已提交超时或失败终态，随后收到原查询结果或旧执行者回调
- **THEN** 系统不重新推进父流程，按来源和权限保存必要审计，不能修改终态或使断点重新有效

## REMOVED Requirements

### Requirement: 显式结束与执行限制
**Reason**: 用户于2026-11-05确认首版不提供用户主动取消整轮问答；运行限制仍需保留，不再与用户结束操作绑定。
**Migration**: 由“逐轮问答与简化交互”和“运行限制与系统收尾”替代。已有取消历史保持可读，不继续暴露用户取消入口或取消工具；系统期限、失败收尾和旧执行者写入保护保留。
