## ADDED Requirements

### Requirement: Maintenance 判断长期记忆维护必要性
系统 SHALL 按每个入口主 Thread 单独累计新增有效用户对话，将自动记忆检查间隔设置为 10 轮。达到条件时，由 Maintenance 做程序检查并协调模型根据有效对话及已有记忆判断必要性；只有需要时才后台调用记忆 Agent 总结，不强制产生记忆。取消旧行程确认及三份 TripPlan 门槛，内部模型、工具和 Item 不计用户轮次。明确记忆操作仍由当前入口模型使用工具，不等周期阈值，不做关键词检测。

#### Scenario: 对话未形成行程
- **WHEN** 新增有效对话达到 10 轮检查条件，但这些对话没有形成已确认的行程
- **THEN** Maintenance 仍检查有无长期记忆价值，有必要时后台执行记忆归纳，不要求补充行程确认标记

#### Scenario: 判断不需要记录
- **WHEN** Maintenance 协调的必要性判断认为本批有效对话无需更新长期记忆
- **THEN** 系统不调用长期记忆存储 Agent，记录本批已完成必要性检查，无新增对话时不重复检查同批内容

#### Scenario: 没有长期价值的信息
- **WHEN** Maintenance 已启动记忆归纳，但记忆 Agent 判断没有值得新增或修改的长期记忆
- **THEN** 系统接受空更新，不新增虚构偏好，也不把此次归纳当成失败

#### Scenario: 后台执行
- **WHEN** 达到检查条件并由 Maintenance 接纳后台记忆维护
- **THEN** 正常答复不等待必要性检查、总结或写入，任务使用独立工作租约和预算，受理不等于已保存

### Requirement: 用户统一记忆与领域按需读取
系统 SHALL 按用户统一维护长期记忆，区分通用、差旅等领域，由相应 Agent 按当前任务需要读取。记忆所属领域不产生另一套用户身份或独立副本，创建新 TravelThread 不清空有效长期记忆，用户当前要求优先于冲突的记忆。读取继续遵守撤回、来源有效性和既有隔离规则。

#### Scenario: 新差旅线程使用已有偏好
- **WHEN** 当前用户新建独立 TripPlan 与 TravelThread，已有允许使用的差旅长期偏好
- **THEN** 差旅上下文按需采用该用户有效记忆，不复制旧子线程内部历史，也不因线程新建丢失长期偏好

#### Scenario: 两个入口分别计数
- **WHEN** 同一用户在通用和差旅入口的不同主 Thread 分别进行对话
- **THEN** 两个主线程各自累计 10 轮检查周期，已保存的用户长期记忆仍按领域和有效性共享

### Requirement: 相关长期记忆由程序装配
系统 SHALL 按用户、任务和领域选择相关有效长期记忆，装配进通用或差旅相应决策阶段的输入，不要求为读取已有记忆先触发归纳。没有相关记忆时作为空记忆继续当前任务，不因此额外调用总结 Agent或强制追问。

#### Scenario: 使用已有记忆不触发维护
- **WHEN** 差旅规划需要已有有效偏好，但当前没有记忆维护必要性
- **THEN** 系统直接装配相关偏好，不把记忆读取等同于调用记忆存储 Agent

### Requirement: 对话归纳的覆盖范围与一致提交
系统 MUST 记录必要性检查范围和实际总结范围，既有用户隔离、撤回和来源任务隔离继续生效。Maintenance 判定无需总结时记录已检查，不冒充已总结；归纳成功即使空更新也推进本批总结覆盖，技术失败不得推进未成功阶段覆盖。必要性判断及归纳使用稳定操作身份，恢复优先复用已保存输出。记忆变更及覆盖以版本和幂等保护提交，后台推断不得覆盖明确记忆或复活已撤回信息。

#### Scenario: 空更新后的下一次检查
- **WHEN** 上次归纳成功但返回空更新，之后没有新增有效对话
- **THEN** 系统不重复分析相同已覆盖内容，不无意义地新增记忆修订

#### Scenario: 归纳失败
- **WHEN** 模型调用、输出解析或记忆提交发生技术失败
- **THEN** 保留已有记忆，不推进未成功处理批次的覆盖记录，按维护任务错误策略处理

#### Scenario: 用户明确操作记忆
- **WHEN** 用户明确要求记住、修改、撤回或重新分析偏好
- **THEN** 系统执行对应操作，不要求先等待自动归纳阈值；普通保存和撤回不额外调用分析模型，重新分析独立记录

## REMOVED Requirements

### Requirement: 有效长期记忆直接注入
**Reason**: 旧条款固定 Main/Verify 角色和旧默认值；新架构保留双入口与专业计划工作线程，用户已确认用户统一记忆、按领域和当前任务读取。
**Migration**: 由“用户统一记忆与领域按需读取”和“相关长期记忆由程序装配”替代；保留当前用户要求优先、有效修订、撤回、来源隔离和空记忆不触发维护的边界，不沿用旧角色命名。

### Requirement: 偏好归纳遵循原版低频触发
**Reason**: 用户确认每 10 轮新增有效对话检查，并在 2026-11-05 交接明确由 Maintenance 承担程序检查与模型必要性判断，有必要才后台归纳，允许空更新。
**Migration**: 由“Maintenance 判断长期记忆维护必要性”和“对话归纳的覆盖范围与一致提交”替代；保留显式操作、撤回、来源隔离、增量覆盖、版本与调用计量。旧 covered_trip_ids 不直接当新覆盖位置，物理迁移见数据库设计。

## MODIFIED Requirements

### Requirement: 偏好和摘要遵循任务隔离
系统 MUST 从后续自动上下文排除已标记失效来源所产生的偏好及摘要；混合摘要含有被排除来源时不得继续直接使用，同时保留更早仍有效的信息。旧流程被新问题替代的任务继续保留其来源排除，移除用户暂停、继续及取消交互不使旧来源重新有效。

#### Scenario: 排除旧任务偏好
- **WHEN** 旧暂停任务保存了独特偏好，后来已被替代并标记来源排除
- **THEN** 新流程保留其历史可读性，但不把该偏好或派生摘要自动装配到模型输入，也不因此重新提供暂停任务替代交互

#### Scenario: 有效来源仍可使用
- **WHEN** 同一用户还有其他来源有效且未撤回的偏好
- **THEN** 系统按原授权和来源规则读取这些偏好，不因排除旧任务而清空全部记忆

#### Scenario: 回退有效修订
- **WHEN** 被排除的偏好曾覆盖更早仍有效的信息
- **THEN** 系统排除失效值并按最新已接受记忆及条目来源使用仍有效的信息，不通过回退更早整份快照绕过撤回或复活已失效值

#### Scenario: 混合摘要失效
- **WHEN** 摘要包含多个来源任务，其中一个已被排除
- **THEN** 系统停止使用受影响摘要，从允许来源重建或暂时不提供该摘要，不泄露被排除内容
