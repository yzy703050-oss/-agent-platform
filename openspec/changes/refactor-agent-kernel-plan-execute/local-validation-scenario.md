# 本机最小验证场景

更新：2026-11-06。本文件对应[当前Design](design.md)和[任务状态](tasks.md)，只保留当前架构的验证路径。

## 1. 拓扑与隔离

- 目标：2 API、2平台Worker、2 Travel、1 Maintenance；独立RAG及构建worker。
- 依赖：同一PG实例的隔离测试库/不同schema及角色、真实Kafka、Redis；参数起点见[整体架构](../../../docs/architecture-final/README.md)。
- 平台Worker分entry/Dispatch池；Kafka只分发子Agent调用，Travel经MCP持久受理，RAG同步调用。
- 使用脚本化模型/供应方响应和协议模拟RAG完成第一层集成；真实RAG与真实模型另行验收，正式交付范围不因模拟阶段缩减。
- 专用启动配置只指向本机测试端点，不覆盖.env或打印密钥。迁移为独立串行步骤，不能用旧服务启动自动迁移开发数据。

此前观察本机约16GiB内存，Docker/Redis等环境未完成验收；实际资源与依赖需开跑前重新核验，不根据旧观察承诺完整拓扑可直接启动。

## 2. 最小正常流程

1. API A接纳问题，API B授权查询并订阅同Run；同请求幂等、不同活动请求冲突。
2. 入口直接查询不创建计划；规划委派保存父现场/依赖/Outbox，父waiting释放槽。
3. Publisher轮询发送Kafka，Dispatch持久接手后通过MCP提交；Travel独立执行并同步查询工具。
4. 平台收集真实结果，原父调用恢复并完成；默认总期限仍为接纳后300秒。
5. 页面断流/换API后带游标补读，恢复快照与最终消息，不再次执行问题。

## 3. 必做故障场景

| 场景 | 观察结果 |
| --- | --- |
| 发布后未标已发、offset确认后Dispatch退出 | 原消息/原身份恢复，不丢任务或重复创建Task |
| MCP已受理但响应丢失、同key并发提交 | 唯一Task；不同hash冲突；按原key找回 |
| Travel/平台执行实例退出、旧实例恢复 | 新epoch接管，旧代次无法有效提交 |
| not_before未到/到期、Publisher重启 | 不提前发送，到期恢复；旧资格不能复活 |
| 最终failed及部分结果、重复/迟到结果 | 真实失败交父、不自动新Task；终态不复活 |
| 三次退避、全局到期、waiting长等待 | 次数不清零、不叠乘、不延长总期限 |
| Redis故障/切换丢许可、跨进程竞争 | PG硬预算/许可守上限，不能每实例各自放满 |
| SSE丢通知/缺delta、慢客户端、API切换 | PG补读/快照恢复，Worker不被慢连接阻塞 |
| 不同schema运行角色访问对方业务表 | 越权被拒，业务通过受控接口交互 |

模拟供应方需允许超过平台限制的接收能力并独立计数，否则无法检出平台超额。记录固定输入、错误脚本、实例ID、业务状态及真实调用数。

## 4. 验收分层

可靠性、隔离和恢复必做；QPS/容量递增扫描选做。真实RAG另测Milvus、中文BM25、Embedding/Rerank、完整证据、索引/删除/回退及离线消融。真实模型与在线供应方独立记录；无测量不写提速/QPS或跨主机容灾。

本轮只整理文档；后续按详细计划实施并运行测试，不启动旧程序代替新链路验证。
