## 2. 保留的关键备选

| 备选 | 本次未采用的原因 | 何时再考虑 |
| --- | --- | --- |
| 仅MCP＋PG，不用MQ | 用户最终选择Kafka负责调用分发 | 没有实际积压/分摊价值，且明确决定简化时 |
| 子Agent直接消费Kafka | 外部服务会依赖平台消息协议；当前统一由Dispatch转MCP | 只接同构内部执行器、无需通用MCP边界时 |
| 原生延迟MQ / Kafka retry Topic | 当前Kafka常规Topic不是现成任意延迟队列，应用转发增加一套调度 | 持久延迟量、精度或PG负载有实测瓶颈时 |
| Redis ZSET闹钟 | 增加PG/Redis双写、认领和丢键重建；已有PG/Outbox可闭环 | 到期调度成为独立瓶颈，值得承担恢复成本时 |
| Redis Pub/Sub主动唤醒Outbox | 轮询已满足首版；提示可能丢失、惊群，仍需扫描兜底 | 发现延迟或空扫描成本实测明显时；只能提示、不能承担可靠交付 |
| 平台/Travel分开PG实例 | 本机先以schema/权限隔离降低资源与部署成本 | 独立扩容、运维或故障域成为需求时 |
| Kafka事实事件总线/历史回放 | 当前只做命令分发，没有多个独立订阅业务 | 审计/统计等各自消费同批事件时；回放不重做模型或外部副作用 |

微服务、多Agent协作并不天然需要MQ。当前Kafka的价值在分发缓冲和消费组分摊，代价是重复投递、Outbox及受理恢复；简历只写实现与实测证据。工具内存timer适合短退避，次数/结果/预算仍需持久化，不能作为唯一恢复依据。

本日技术取舍：公共授权/预算采用同PG的私有control协调schema＋受限函数，利用本地事务锁裁决撤回与提交竞争；未选另建HTTP授权服务，以免仍需解决远端检查至本地提交的竞争。此为原权限/预算要求的技术实现选择，不是新增产品行为，也不开放平台/Travel互读业务表；详见原工程协议及复核记录，不在此复制接口和表字段。

其他已明确的业务规则直接看当前设计，不再逐条列举被否决的旧角色、表数、提示词和讨论过程。后续只有改变当前边界的新决定才更新本页。
