# 交付边界、验证与简历证据

版本：2026-11-06架构基线v1。返回[总览](README.md)。任务状态仍统一维护在原[tasks.md](../../openspec/changes/refactor-agent-kernel-plan-execute/tasks.md)；本页给出验收结构，不另立实施完成清单，也不代替详细TDD计划。

## 1. 当前代码与目标的差距

现有Go项目有Gin API、Cookie/Session/CSRF、Eino运行封装、差旅领域服务、PG迁移和React前端。当前bootstrap仍有单实例装配/锁，MCP RAG仍是stdio客户端；新Kafka/Outbox/Dispatch与独立Travel可靠链路尚未实现。

providerhttp已有最多3次总尝试、1s/2s抖动、Retry-After和进程内熔断，目标改为最多3次重试/4次总尝试需适配唯一责任方。当前Run repository主要使用行锁和version递增，不代表全部目标状态已有expected_version CAS。前端fetch SSE解析也需补跨重连游标，不能仅因后端支持after就宣称前端已支持。

没有把本次文档写入当作产品完成；旧设计材料检查和同进程假模型测试不能证明新跨进程协议。

## 2. 身份、SSE与前端

沿用随机不透明Cookie、PG Session摘要、CSRF和来源校验，不引入JWT。首版不缓存认证正结果，跨API登录/撤销按PG事实核验；SSE周期复核权限。页面连接、page_leases和任务执行租约分开，浏览器关闭不暂停任务。

正式Run事件在PG有单调seq，与状态/结果同事务；Redis通知仅提示补读，API周期回PG，乱序通知不直接跳游标。临时delta带stream_id/lease_epoch/delta_seq，不推进持久SSE ID；部分输出定期快照、最终/错误及时落库，重连以快照和消息恢复，不承诺逐token可靠回放。

平台API A接纳后，API B必须能授权查询/订阅同Run；前端带游标退避重连，不新建任务。旧流或旧epoch不得污染新输出；慢客户端队列满或写超时关闭连接，不阻塞Worker。反向代理需正确转发SSE、避免不当缓冲，用户不看到Planner原始内部日志。

## 3. 核心故障验证矩阵

| 类别 | 场景 | 必须证明 |
| --- | --- | --- |
| 接纳 | 并发相同幂等键/不同请求同会话 | 原Run唯一；不同活动请求冲突，无重复消息 |
| 父挂起 | 序列化/事务失败、提交前后退出 | 无可靠现场不发子工作；waiting有可恢复依赖 |
| Outbox | 多Publisher竞争、无主动通知、标记窗口退出 | 到期扫描有效、owner/epoch正确、允许重发但无丢工作 |
| Kafka | 重复旧seq、offset失败、分区重分配、DB异常 | 可靠接手后才确认；确认后退出仍由PG恢复；DB异常不误确认 |
| MCP受理 | 响应丢失、并发同key、参数冲突、换实例 | 仅一个持久Task，同key同参找原任务，不覆盖参数 |
| 远端执行 | queued重启、运行租约过期、旧实例恢复 | 合法实例接管原Task/现场，旧epoch有效提交被拒 |
| 结果收集 | 保存前后退出、结果重复、父已终态 | 幂等收集与父ready，迟到不复活 |
| 最终失败 | 远端failed带部分结果、同key重提 | 原失败/部分结果交父，不自动创建新Task，不重置旧终态 |
| 数据权限 | 平台/Travel各自运行账号访问另一schema | 越权被PG拒绝，业务交互经MCP/受控接口；共实例不等于共享业务读写权 |
| 持久延迟 | not_before之前/之后、Publisher退出/接管 | 不提前发送，到期恢复一次有效分发资格，旧seq不能复活 |
| 租约/期限 | running正常续租、waiting无续租、global到期 | 续租只续执行权，等待和恢复不延总期限 |
| 重试 | 三次退避、Retry-After、重启、跨层故障 | 四次总尝试上限、原次数不清零、不相乘 |
| 资源 | 两Worker/两Travel争用模型或RAG | 共享许可不乘副本数，独立供应方观测计数 |
| Redis | 丢许可/断连/主切换，丢SSE提示 | 新调用保守、持久硬上限有效、事件可补读 |
| 领域 | 首版/后续Patch、冲突、Task局部改动 | 正式版本/回执一致，受影响全查，无关Task保留 |
| 来源 | 未知价格、假候选、跨用户、来源撤回 | 不编造/越权/复活失效来源 |
| 记忆 | 十轮、无需归纳、空更新、失败/恢复 | 正确游标、稳定操作、后台不阻塞答复 |
| RAG | 授权/索引/删除/降级/重启 | 完整证据及真实路径，未存可有界重算，已存复用 |
| UI/SSE | API切换、流缺口、旧delta、慢连接 | 快照/最终消息正确，无重复执行或暂停 |

最终失败按用户确认收集失败及可用部分结果交父，不得通过换key自动重开任务绕过该策略。若未来引入ZSET、主动唤醒或原生延迟broker，必须新增相应故障验证，不能只替换配置名。

## 4. 模拟与真实依赖分层

本机最小集成使用脚本化模型/供应方/HTTP MCP响应，真正运行Eino、PG、Kafka、Redis及SSE，不用玩具调度器替代平台。模拟标识明确，不冒充推理/检索质量、真实延迟、供应方能力或付费模型验收。

测试全局并发时，模拟供应方自身不能先限成2并发；应允许接收并独立计数，才能检出平台额度超限。固定请求、延迟/错误脚本及实例ID便于复现。性能基准为选做，首版先留下可靠性、隔离和恢复证据，不虚构QPS。

真实RAG另外验收Milvus、中文BM25、Embedding/Rerank模型、TXT/PDF、可信原文gold、索引发布/回退/删除与消融。真实模型和供应方检查单独记录环境/凭据与结果，没运行就明确未验证。

本机此前只读观察为Windows 11、5800H/8核16线程、约16GiB内存，某次检查仅约2.8GiB可用；资源状态会变，不能据此保证完整多实例可直接启动。Kafka/Redis/Docker等环境未就绪验收。真实启动前准备隔离环境和资源，不自动关闭程序、安装服务或下载模型，不读取/打印.env密钥。

## 6. 开发流程与检查命令

原OpenSpec proposal/specs/design/tasks是正式依据。设计复核后使用writing-plans生成引用它们的详细实施计划，写清文件/接口、先失败测试、实现、验证及完成条件，再由用户选择实施单代理或多子代理。当前不因存在多个Agent角色就自动派Codex子代理。

一次apply中按适用TDD逐任务实施并更新tasks，完成后进行任务证据审核、实际测试、代码审查与规格核对，再archive和分支收尾。当前CLI没有独立verify工作流时，明确说明并人工逐条核对，不能用validate代替产品一致性证明。

现有CI基础命令：

```text
backend:
  go test -race ./... -count=1 -timeout 180s
  go vet ./...
  go build ./cmd/server

frontend:
  npm run test -- --run
  npm run build

repo:
  openspec validate refactor-agent-kernel-plan-execute --strict --no-interactive
  openspec validate refactor-rag-mcp-retrieval-service --strict --no-interactive
```

新进程入口/真实依赖集成命令随实施计划补齐。文档轮只做本地链接/结构/编码与OpenSpec材料检查，不为了文档变更安装依赖或运行会迁移数据库的旧服务。
